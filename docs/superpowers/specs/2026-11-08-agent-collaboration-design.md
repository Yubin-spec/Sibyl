# Agents Calling：跨工具 Agent 协作设计

日期：2026-11-08
状态：待评审
范围：第一阶段（作者本人日常使用）

## 1. 意图

在同一台电脑、同一个仓库里，同时使用 Claude Code 和 Codex 的开发者，经常需要两个工具配合完成一件事。今天的做法是人来回转述：把 Claude 的结论复制给 Codex，再把 Codex 的回复贴回 Claude。转述会丢上下文、会失真，人也变成了慢速的中间人。

要解决的是这一句话：

> 人对 Claude 说「你和 Codex 协作解决这个」，然后继续做别的事；两个 Agent 自己分工、自己商量、自己在仓库里动手，最后交回一个人类能验收的结果。

协作的形态是**主从、双向**：

- 谁接到人的那句「你和 X 协作」，谁就是**主导方**。
- 主导方派活、给定范围、验收结果。
- 另一方是**工作方**：在它自己的工作树里读代码、改文件、跑测试，然后把活交回来。
- 角色由那句话决定，不由工具决定。Claude 可以主导 Codex，Codex 也可以主导 Claude。

## 2. 目标

### 第一阶段必须有

- **G1 对称**：Claude→Codex 与 Codex→Claude 都能派活并动手改文件。今天只有前者可行。
- **G2 三档负载**：能按活的形状自动选择「问一下 / 派个活 / 分头干」，不需要人每次指定档位。
- **G3 可验收**：工作方交回结构化的交工报告——改了哪些文件、diff、跑了什么、还剩什么没做。主导方据此验收，而不是相信一句「我改好了」。
- **G4 写边界**：同一仓库下，同时活着的工作方路径不得重叠；共享文件只能由主导方修改；派活前对未提交改动做快照。
- **G5 只读观测页**：一个本地网页，能看清「哪个 Agent 在跟谁说什么、为什么停了、改了哪些文件」。
- **G6 装得起来**：Windows 优先，一次安装到位，不需要读 README 才知道下一步。

### 非目标

- 不做原生桌面界面。App 是以后的高级壳，第一阶段不做。
- 不做多人协作、团队共享、云端中转。
- 不做插件市场、自定义路由。
- 不做无边界的多 Agent 自由对话。
- 观测页第一版不做任何写操作（停止、合并、重派都留到以后）。

### 反目标（做到了也算失败）

- 两个 Agent 同时写同一个文件，覆盖掉人或其他 Agent 的改动。
- 工作方交回「已完成」，但没有 diff 可核。
- 人必须读 JSON 或者翻日志才知道发生了什么。
- 为了看一眼状态而必须打开某个 App。
- daemon 的生命周期绑死在任何界面进程上。

## 3. 约束

- Node.js >= 26，保持零第三方 npm 依赖（现有约定）。
- 主力开发环境是 Windows 11；macOS 由 `develop` 分支那条线负责。
- 仓库里已经存在、应当复用而不是重写：
  - `native-mcp.mjs`：MCP stdio 服务，按工作目录自动注册，提供 `bridge_*` 工具。
  - `control.mjs`：任务编排、consult 生命周期、看门狗、HTTP UI API。
  - `consult-policy.mjs`：预算与去重策略。
  - `bridge.mjs`：跨设备协议与进程启动。
  - `workspace.mjs`：SQLite 持久化（项目、会话、线程、消息、设置）。
  - `scripts/spawn-codex-chat.mjs`：Codex app-server 进程与 RPC。
- `develop` 分支已重构为 `src/` 布局并改名为 Agents Calling；`feat/windows-support` 仍是旧扁平布局，有 11 个未合并提交和若干未提交改动。第一阶段在 `feat/windows-support` 上、沿用现有的扁平文件名开发；迁移到 `src/` 布局的安排见 §11.1。

## 5. 我的判断（写进设计，可被推翻）

- **档位由 Skill 判断，不让人选。** 人只说「你和 X 协作」，选档由 Skill 依据任务形状决定；判断错了纠正一次的成本远低于每次都要指定。
- **工作方一律在独立 `git worktree` 里工作**，即使是串行档位。这样和主导方未提交的改动天然隔离，验收也有现成的 diff。
- **未提交改动先做快照再派活。** worktree 从 commit 开出，看不到主导方工作区里的未提交改动；不处理会让工作方基于旧代码干完回来必冲突。
- **路径租约是硬约束**：任务单必须声明可碰路径，两个同时活着的工作方路径重叠就拒绝，降级成串行或只读核对。
- **共享文件归主导方**：`package.json`、锁文件、共享类型、配置，工作方只能请求修改。
- **观测页是纯读模型**，独立端口，daemon 自己管理生命周期。
- **daemon 不带任何界面依赖**，App 以后只是一个指向 localhost 的窗口。

### 补充判断（builder 检查后落定）

- **工作方生命周期归 daemon，不归 MCP 进程。** 今天 `bridge_spawn` 是调用方 MCP 进程的子进程，进程一退就全死；观测页也就看不到活着的 worker。改为 daemon 持有 worker，`native-mcp` 只做转发。工作在主导方聊天结束后仍然跑完，报告落库，超时后标记为「孤儿」并停止。
- **派活是异步的。** `worker_start` 立刻返回 `workerId`，`worker_result` 拉取结果，和现有 `bridge_consult`/`bridge_consult_result` 一个形状。不阻塞工具调用——MCP 侧超时（35 秒 / 120 秒）远小于一次真正的派活。
- **报告写文件，正文只回摘要。** 完整 diff 落盘（`.sibyl/reports/<workerId>.patch`），工具返回里只给摘要、文件清单和路径。diff 动辄几 MB，塞进工具输出会撑爆上下文，也撞上 stdin 行长度上限。
- **快照只复制，daemon 永不向主导方分支提交。** 做法：把主导方工作区（含未跟踪、排除 ignore）复制进工作方 worktree，在工作方**自己的分支**上提交一个快照 commit。主导方的分支和历史完全不动——他们现在就有 9 个未提交文件，任何自动提交都可能把半成品带进历史。非 git 项目在第一步就明确拒绝，而不是降级成不可控的行为。
- **合并由主导方执行。** 主导方本来就有 shell，让 daemon 抢着做 `git merge` 只是多一套实现。daemon 的职责是租约与**前后 ref 比对**：派活后 worker 分支之外的 ref 若有变动，报告里点出来。冲突不自动解，停下并进观测页的「需要人拍板」。
- **工作方的 git 纪律**：允许 `status`/`diff`/`log`/`show` 之类只读命令；`reset`/`branch -D`/`push`/`config` 这类会动共享 `.git` 的命令禁止。靠 ref 前后比对兜底，因为 worktree 共用同一个 `.git`。
- **共享文件集合**：内置默认（`package.json`、各类锁文件、`tsconfig`、配置目录）+ 项目级覆盖文件。工作方要改只能通过交工报告里的「请求变更」提出，由主导方落地。
- **第一阶段的权限姿态**：工作方无网络、不装依赖。本仓库零 npm 依赖，worktree 里通过目录联接（Windows junction / 符号链接）复用主仓库的 `node_modules`，跑测试不需要安装。工作方遇到需要确认的命令时，必须把它变成报告里的阻塞项并附原始错误，而不是静默跳过。

## 6. 三个档位

| 档位 | 适用 | 机制 | 是否合并 |
|---|---|---|---|
| 问一下 | 对方只需看、评、核对 | 现有 `bridge_consult`，只读 Worker | 不合并 |
| 派个活 | 一个动手，另一个等着或干别的 | 开一棵工作树，工作方改，交回分支 + 报告 | 主导方验收后合并 |
| 分头干 | 两边同时改不同部分 | 每边一棵树，路径租约保证不相交 | 顺序合并 |

三档共用同一套工作方生命周期：`worker_start` / `worker_turn` / `worker_close`。区别只在开几棵、要不要合并。（第一阶段实现上沿用 `bridge_spawn` / `bridge_spawn_turn` / `bridge_spawn_close` 并新增 `tool` 参数；等 `scope` 与租约落地时再统一改名。）

### 分头干的确切拓扑

主导方是活的 Agent，它的工作目录绑在会话上，**不可能被搬进 worktree**。所以拓扑只有一种：

- 主导方留在**自己原来的工作区**里改。
- 每个工作方各开一棵 worktree（副本来自派活那一刻的快照）。
- 所以「分头干」= 1 棵主工作区 + N 棵工作方工作树；第一阶段 N 收在 1。

**租约必须同时约束主导方。** 派活时主导方登记的 `scope` 也进租约表；主导方在工作区里改租约之外的文件不受限，但要改到工作方 `scope` 内的文件，必须等工作方交工。否则「一个改一个等」也是必冲突。

**交付用补丁，不用分支合并。** 工作方在自己的分支上从快照 commit 往后提交，交工时给出「快照 → 工作方 HEAD」的补丁（已在 `.sibyl/reports/<workerId>.patch`）。主导方把自己那部分改动一起放进工作区，用三方合并把补丁贴上去。这样主导方的分支和历史始终不动，也不需要它先提交半成品才能合并。多个工作方按顺序贴补丁；因为租约保证路径不相交，正常情况下都能干净贴上。

### 交工报告（G3）

工作方结束时必须交回：

- 工作树路径与分支名
- 改动文件清单（新增 / 修改 / 删除）
- 完整 diff，或超出体积上限时的摘要
- 跑了哪些验证（测试、构建、lint）及其结果
- 未完成项与已知风险
- 阻塞原因（若有）

报告是给人看的，也是给主导方做验收依据的。

### 写边界（G4）

- 派活前检查主导方工作区是否有未提交改动；有则先快照（WIP commit 或复制），并把快照点记在任务单上。
- 任务单声明 `scope` 路径集合；daemon 维护活跃租约表，重叠即拒绝。
- 合并回主导分支时串行执行，同一时刻只有一把写锁。

## 7. 观测页（G5）

本地 HTTP 页面，只读，默认只监听回环地址。可以在浏览器里打开，也可以在 VS Code / Cursor 的 Simple Browser 里当 IDE 面板用。

第一版展示：

- **线程列表**：发起方 ↔ 目标、项目、档位、状态（跑着 / 等回答 / 已停 / 待合并）、耗时。
- **单线程详情**：每一轮的问与答、停止原因的人话解释。
- **工作方**：工作树路径、分支、改动文件数、diff 摘要、已合并 / 待合并。
- **需要人拍板的事**：合并冲突、超时、审批卡住、路径租约被拒。

页面上不出现任何按钮。任何操作都在对应的 Agent 对话里说。

## 8. 与 App 的关系

App 不是被砍掉，是被降级成以后的一个壳。

边界只有一条：**daemon 自己启动、自己存活、自己退出；App、网页、IDE 都只是连上来的客户端。**

`develop` 上「启动时接管后台进程」的提交方向相反（后端成为 App 的子进程），处理分叉时需要调整，否则以后无法从网页或 IDE 独立访问。

## 9. 阶段划分

**A. 补对称**
把 `spawn` 泛化成 `worker_start(tool, project, scope, sandbox)`，补一个能写文件的 Claude 工作方启动器（headless CLI 或 Agent SDK）。目标是 Codex 能派活给 Claude。

**B. 三档 + 验收 + 边界**
三档档位、路径租约、共享文件规则、未提交改动快照、结构化交工报告、按档位重设时间预算。

**C. 观测页**
只读本地网页，含线程、轮次、工作方、待裁决事项。

**D. 打包**
Claude Code 插件包（MCP + Skill + 斜杠命令）与 Codex 侧的 `AGENTS.md` 片段 + `codex mcp add`。目标是一次安装。

观测页（C）可以提前到 B 之前做，因为它便宜且立刻降低调试成本。

## 10. 现有实现里会被这套设计改掉的部分

- `spawn` 写死 Codex：需要泛化到任意工具，并补 Claude 工作方。
- `consult` 的预算为问答设计（单次总时长 180 秒、120 秒无进展即停、10 分钟 12 次）；三档里的「派个活 / 分头干」不能共用这套数字。
- `spawn_turn` 只回文本，没有 diff 与文件清单，无法支撑验收。
- `approval policy = never` 意味着工作方遇到需要确认的命令会直接失败，而不是来问人；跑测试、装依赖会卡在这里。按 §5 的权限姿态处理：不装依赖、复用主仓库 `node_modules`，其余一律变成报告里的阻塞项。
